# Codex 终端支持评估

日期：2026-10-25。基线：v0.22.0 / aff519b。本机 CLI：0.164.0。

状态：完成代码与官方文档评估，尚未进行双客户端原型或真实模型验证；本文件不授权实施全部方案。

## 建议

保留托管模式作为默认。优先验证“同一个 app-server，网页与 Codex 原生 TUI 各为客户端”，不要先照搬 Claude 的 PTY、日志与 Hook 桥接方案。

先投入最多 2 个工程日验证方向；若证据明确，再允许完整可行性验证扩展到 2–4 日。只有同线程事件、审批、断线及后台任务生命周期通过，才做实验性本地终端入口。验证失败时，延期终端支持，继续完善结构化托管功能。无需为了提供终端入口承担长期屏幕解析维护。

## 当前模式是什么

当前 `internal/codex/rpc.go` 启动本机 `codex app-server --listen stdio://`，以 stdin/stdout 传送双向 JSON-RPC 消息，JSONL 逐行编码。`internal/codex/process.go` 用 thread/start、thread/resume、turn/start 和 turn/interrupt 管理线程与轮次；网页自行展示回复、工具和审批。

该模式没有 Codex TUI，也没有为其界面创建 PTY，但运行的是本机 Codex 引擎。文件读写、命令执行、沙箱、工具与模型循环仍由引擎处理。“没有模拟终端界面”不代表“不能执行终端命令”，也不代表用普通聊天 API 自行拼了一个能力缩水的代理。

模型实际效果仍受相同模型、账户权限、工作目录、配置、指令及工具可用性影响；不承诺与任意原生 CLI 配置逐项等价。

## 功能差异

| 能力 | 当前项目 | 原因与处理方向 |
| --- | --- | --- |
| 生成与修改代码、执行构建/测试、工具结果 | 已接结构化事件 | 无需增加原生终端即可完成 |
| 图片输入、线程恢复、停止、排队、压缩 | 已实现适配 | 不因缺少 TUI 而天然丢失 |
| Skills、MCP、项目指令 | 由本机 Codex 读取配置；已有工具事件和技能文本入口 | 不保证所有插件、认证及交互流程已适配或端到端验证 |
| 原生终端的菜单、快捷键、编辑器、完整斜杠命令 | 网页只实现自己的子集 | TUI 的操作界面不通过 turn/start 自动提供 |
| 执行中追加指令 | 当前串行排队 | 官方有 turn/steer；可独立补到托管模式 |
| 完整审批语义 | 桥接命令、文件和用户提问；主要为本次允许/拒绝 | 暂无完整会话级授权、权限增补、MCP 表单/认证等协议覆盖；未知请求拒绝，不假装成功 |
| 计划、差异、Token、额度等展示 | 部分事件已收为 status，未全部转换成专用视图/统计 | 属于适配与展示缺口；终端支持不会自动补好网页 |
| fork、goal、原生 review 等专用流程 | 未提供完整原生操作入口 | 可按需求接相应 RPC；自然语言“请审查”不等于原生 review 模式 |
| 本地终端与网页操作同一个活跃运行 | 尚未支持 | 当前 stdio 通道只服务宿主适配器 |
| 停止后在 CLI 恢复同一个历史线程 | 可作为接力方向；应先释放原运行 | 恢复持久上下文不等于接入原进程，不能保证后台任务存活 |

已实现表示存在代码及相应回归，不代表所有能力都已使用真实模型全面实测。

## 新证据：官方 TUI 可以连接 app-server

[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server) 给出了 app-server WebSocket listener 与 `codex --remote` 的连接方式；[CLI 命令参考](https://learn.chatgpt.com/docs/developer-commands?surface=cli) 也列出 resume 的 remote 模式。本机 0.164.0 的 `codex --help`、`codex resume --help` 和 `codex app-server --help` 已核实这些参数存在。

候选命令形态（仅说明架构，尚未验证完整连接流程）：

```text
codex app-server --listen ws://127.0.0.1:<port> <认证配置>
codex resume --remote ws://127.0.0.1:<port> <thread-id> --remote-auth-token-env <环境变量名>
```

网页继续由 cc-remote 连接这个 app-server；原生终端使用另一个协议连接接入同线程。必须是同一个运行中的引擎，不是另外启动一个引擎恢复同一份历史。

注意：官方当前将 WebSocket transport 标为 experimental / unsupported for production。帮助中有参数，只能证明连接入口存在，不能证明本项目的多客户端审批和生命周期已经正确。

## 路线比较

以下是单名熟悉项目的工程师的粗估工程日，不是交付承诺；不确定性主要在 Codex 版本与多客户端语义。

| 路线 | 估算 | 判断 |
| --- | --- | --- |
| 保持托管，按需求补 steer、额度、统计和原生操作 | 每项约 1–3 日，复杂交互另计 | 默认方向；多数能力缺口不需要 TUI |
| 同 app-server + 原生 TUI，受限单控制端实验版 | 完整 gate 2–4 日；最小交付累计约 7–12 日 | 首选终端路线，有条件实施；结构化同步范围需明确 |
| 单独增加网页终端显示 | 约 3–6 日，取决于首期是否已包含 | 可复用 PTY 显示；不等于结构化双端同步已完成 |
| 双端结构化一致、审批同步、断线补偿和完整保活 | 累计约 20–35 日 | 成本较高；没有明确需求时不建议承诺 |
| 独立 Codex TUI + PTY + rollout/Hook 还原网页 | 粗估 10–20 日或更多 | 次选；完整审批/状态/恢复带来持续版本维护 |
| 停止托管后导出原生 resume 接力入口 | 约 1–3 日 | 成本较低，但必须明确会中断当前运行，不满足无缝接入 |

Codex 当前已有 Hook 框架，不能以“没有 Hook”作为否定理由。但 [官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks) 明确指出 transcript 格式不是稳定接口，且 Hook 信任、事件覆盖与审批仲裁仍须验证。

## 首选路线如何拆分

### 阶段零：限时隔离验证

先用 2 日判断方向是否成立，必要时完整 gate 扩展到 2–4 日；没有新证据不继续延长。固定本机已知版本、独立测试目录和端口，不改用户全局配置，不迁移现有会话，不在本阶段修改正式服务。

必须验证：

1. 宿主协议客户端和 TUI 同时订阅同一 thread；两边发的用户消息均能准确入库且不重复，网页不依赖“只记录自己发的消息”。
2. 从任一端启动轮次，另一端正确显示运行/等待/完成；明确同时提交是排队、steer 还是拒绝，不能误开双轮。
3. 审批由哪个连接接收、谁有权回答、另一端如何撤卡；拒绝、取消、重复回答及审批接收端掉线均有确定行为。可以先采用显式交接控制权，不强求同时回答。
4. 终端断开、网页刷新，不中断运行与子任务；宿主协议连接重连可恢复事件和未决请求，缺失信息不得显示为空闲。
5. TUI 的退出行为不会顺手关闭共享引擎；宿主空闲回收和配置变更不误杀仍连接的终端或后台任务。
6. 使用本机绑定和单独的可撤销认证凭据，端口不直接暴露局域网；确认 Windows npm 启动器、退出和进程树行为。

若只有原生连接能显示画面，而事件/审批/生命周期无法可靠协调，判定未通过；不要靠匹配屏幕文字绕过这些问题。

### 阶段一：本地终端实验入口

- 在现有 JSON-RPC 分发逻辑下增加可选的 WebSocket transport，保留 stdio 默认路线及旧 CLI 支持。不改成全宿主共享一个引擎，初期继续每活跃会话一个 app-server，避免扩大故障范围。
- 新增明确的宿主终端能力标志；网页、CLI 及原生 Codex 分别检测能力。旧服务端、旧 Codex、不支持认证/remote 的版本只显示托管与历史，不发送不支持的操作。
- 命令入口可采用 `ccr --provider codex` 或独立子命令，最终语法在原型通过后确定；不能把 Codex 参数交给 Claude 启动器。
- 控制权先按单写入端设计；观察端只收事件。若上游请求路由支持明确仲裁，再开放双端提交与审批竞争。
- Codex 终端应是 managed runtime 的附属 TUI 视图；不能直接设置现有 `Mode=terminal`，否则会进入 Claude 的粘贴/Hook 分支。
- 当前 Process 的排队、Replay、turn 生命周期和事件去重需要适配外部客户端，不能只替换传输层。现有“设置下一轮生效时重启进程”也要避免踢掉 TUI。
- 没有运行中的工作时可停止/重建引擎并恢复持久线程；不能承诺宿主进程本身重启后保留正在执行的命令与子代理。

### 阶段二：网页原生终端（可选）

在宿主 PTY 中运行连接到同引擎的 Codex TUI，网页终端复用现有显示和尺寸管理。PTY 只承载界面；结构化视图仍来自 app-server，不解析 ANSI 画面还原工具和审批。

只有有明确需求，才进一步考虑多 TUI、远程电脑的原生 CLI 接入、完整双写入、自动接管已经在别处启动的 Codex 会话。这些不属于首期承诺。

## 仓库内的关键耦合

- `internal/codex/rpc.go`：连接断开、写入取消与 Close 目前会连带结束所持 app-server；共享模式要分开连接与引擎生命周期。
- `internal/codex/process.go`：Replay 来自本地队列，尚未处理外部 userMessage；turn/started 仅更新内部 ID。双客户端消息和状态不能直接沿用单控制者假设。
- `internal/server/runtime.go`：启动参数变化会重启进程，空闲回收不识别 TUI attachment。
- `internal/server/terminal.go` 和 `internal/terminal/attach.go`：启动、路由及 CCR 参数仍耦合 Claude；PTY 基础与字节流可复用，Claude trust/readiness/screen 识别不能直接套用。

## 不实施的判据

- 支持依赖修改 Codex 本体、维护私有 fork，或长期解析 TUI 屏幕。
- 未决审批在切换客户端时容易丢失，无法通过显式控制权交接解决。
- 上游 transport/客户端版本变化导致频繁断裂，没有可接受的最低版本范围。
- 原型表明终端获得的价值主要只是少量菜单，而用户并不需要原生终端接力。

满足任一项时可合理选择不支持终端，将预算用于托管功能。当前建议是允许一次小规模验证，尚不承诺发布终端支持。

## 验证范围

本轮只查阅项目代码、官方文档及本机 CLI 帮助；未发起模型推理、未启动多客户端实验、未改正式配置或运行服务。评估中的工作量和可行性条件均有待阶段零校正。
